# Redis 规范

> 本规范结合《阿里巴巴 Java 开发手册（泰山版）》中的缓存相关条款，总结 Redis 在设计、编码与运维阶段需要遵循的最佳实践。

## Key 设计
- Key 统一使用 `业务:模块:含义` 的命名，例如 `auth:verification:email:{identifier}`，字符集限定 `a-z0-9:`。
- Key 避免过长（建议小于 64 字节），禁止使用空格及中文字符。
- 所有 Key 必须设置过期时间，除非确有永久存储需求且经评审确认。
- 使用 Redis 的原子操作（如 `SETNX`、`INCR`）实现分布式锁或计数，禁止以 Lua 以外的不可靠自旋方式。

## Value 与数据结构
- 根据场景选择合适数据结构：
  - 频繁读写、单值场景使用 String；
  - 需要顺序访问的列表使用 List；
  - 需要去重的集合使用 Set；
  - 需要排序排行榜使用 ZSet；
  - Hash 用于存储对象属性，避免序列化整对象。
- Value 序列化统一使用 JSON（或指定序列化协议），避免使用 Java 原生序列化。
- 大 Value（>100KB）需拆分或外部存储，防止网络和内存抖动。

## 业务使用规范
- 缓存与数据库双写时遵循“先写库后删缓存”或“查询更新以缓存为准”等一致性策略；高一致性场景可采用消息队列修复。
- 对高 QPS 接口采用多级缓存策略（本地 + Redis），并设置合适的过期时间及随机抖动，避免同一时间雪崩。
- 避免对单个 Key 频繁执行复杂操作，必要时拆分热点 Key 或使用 Lua 脚本原子化处理。
- 缓存穿透：对不存在的数据写入空值并短期缓存，或使用布隆过滤器预防。
- 缓存击穿：针对热点 Key 设置互斥锁或逻辑过期；缓存雪崩：过期时间加随机值。

## 运维与监控
- 禁止在生产环境执行 `FLUSHALL`、`FLUSHDB`，危险命令需在运维层面禁用或加确认。
- 数据量级受控，单实例内存使用不超过 80%（保留碎片与主从复制开销）。
- 必须启用慢查询日志并监控 QPS、内存、连接数、命中率等指标。
- 主从复制或集群必须定期校验数据一致性，故障时有自动故障转移策略。

> 如业务存在特殊缓存策略，应形成专项设计说明，并在上线前完成容量评估与压测。
