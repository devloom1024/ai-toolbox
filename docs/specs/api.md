# API 规范

> 本规范参考《阿里巴巴 Java 开发手册（泰山版）》以及内部 API 设计经验，总结服务端接口的设计、实现和文档要求。

## 设计原则
- **REST 风格优先**：路径使用名词复数表示资源，例如 `/api/v1/users`；对动作类操作使用子资源或动词后缀，如 `/api/v1/users/{id}/password`。
- **版本管理**：通过路径 `v1/v2` 管理版本，避免通过 Header 控制；重大变更发布新版本，老版本保留兼容期。
- **Idempotency**：PUT/DELETE 保持幂等；对可能重复提交的 POST（如注册/支付）引入幂等键。

## 请求/响应规范
- 所有接口使用 HTTPS，编码统一为 UTF-8，Content-Type 为 `application/json`。
- 请求参数必须校验并返回业务友好的错误码；禁止直接返回框架异常栈。
- 响应结构统一：
  ```json
  {
    "code": 0,
    "message": "ok",
    "data": {}
  }
  ```
  - `code`：0 表示成功，其余为业务错误码；
  - `message`：用户可读信息；
  - `data`：业务数据，可为空对象。
- 分页响应统一包含 `page`, `pageSize`, `total`, `items` 字段。

## 错误码策略
- 业务错误码采用分段策略：`1000-1999` 为通用错误（参数、鉴权、限流等），`2000+` 为各模块自定义。
- HTTP 状态码与业务码同步：客户端错误用 4xx，服务器错误用 5xx，不允许所有错误都返回 200。
- 异常链路必须记录 traceId，方便链路追踪。

## 安全与性能
- 接口需启用认证与鉴权；敏感操作添加风控（如验证码、二次确认）。
- 所有输入参数走统一 XSS、SQL 注入过滤链路。
- 限流与熔断：核心接口应由网关或服务层实现 QPS 限流、熔断与降级策略。
- 避免一次接口返回超 1MB 数据，超限数据需分页或分段拉取。

## 文档与测试
- 每个接口要有对应的 Swagger/Knife4j 文档，包含示例请求和响应。
- 通过契约测试或集成测试验证接口行为，变更前应更新文档并回归测试。
- 发布前执行接口自测清单：含鉴权、异常、幂等、性能等场景。

> 以上条目为基线要求，如需偏离必须经过架构评审并在接口文档中注明原因。
