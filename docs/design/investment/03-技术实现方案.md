## 二、关键设计决策

### 2.1 为什么选择 PostgreSQL 而非 MySQL？

| 对比维度 | PostgreSQL ✅ | MySQL |
|---------|--------------|-------|
| **JSONB 支持** | 原生支持，性能优秀 | JSON 类型性能较差 |
| **复杂查询** | 支持 CTE、窗口函数 | 部分支持 |
| **数据类型** | ARRAY、HSTORE 等 | 类型较少 |
| **扩展性** | 插件生态丰富 | 扩展能力弱 |
| **适用场景** | AI 分析结果、策略配置 | 传统 CRUD |

**决策理由**：
- AI 分析结果需要存储 JSON 格式（多维度评分、关键数据）
- 策略配置需要灵活的 JSONB 存储
- 未来可能需要复杂的分析查询

### 2.2 为什么使用 Zustand 而非 Redux？

| 对比维度 | Zustand ✅ | Redux |
|---------|-----------|-------|
| **学习成本** | 低（几分钟上手） | 高（概念多） |
| **代码量** | 少（无样板代码） | 多（action/reducer） |
| **TypeScript** | 原生支持 | 需要额外配置 |
| **包大小** | ~1KB | ~10KB |
| **性能** | 优秀 | 优秀 |

**决策理由**：
- 投资模块状态管理逻辑简单，无需 Redux 复杂能力
- TypeScript 类型推断友好
- 减少前端包体积

### 2.3 为什么采用 DDD 分层架构？

```
传统三层架构          DDD 分层架构 ✅
Controller           API 层 (薄层，仅路由)
  ↓                    ↓
Service              Application 服务层 (应用逻辑)
  ↓                    ↓
DAO                  Domain 领域层 (业务逻辑)
                       ↓
                     Infrastructure 基础设施层
```

**决策理由**：
- 投资模块业务逻辑复杂（成本计算、AI 分析、策略回测）
- 领域概念清晰（持仓、策略、分析记录）
- 便于单元测试（领域服务独立）

### 2.4 为什么不使用外键约束？

**原因**：
1. **灵活性**：应用层控制关联关系，便于分库分表
2. **性能**：避免数据库级联查询开销
3. **可维护性**：业务变更无需修改数据库约束
4. **分布式友好**：未来拆分微服务更容易

**保障措施**：
- 应用层严格校验关联关系
- 定期数据一致性检查任务
- 完善的单元测试覆盖

## 三、核心设计

### 3.1 AI 智能体架构

#### 设计思路

```
用户请求
  ↓
Super Agent (分诊)
  ↓
根据分析类型分发
  ↓
┌─────────┬─────────┬─────────┐
↓         ↓         ↓         ↓
Research  Strategy  Sector   Portfolio
Agent     Agent     Agent    Agent
```

#### 核心能力

| 智能体 | 职责 | 输入 | 输出 |
|--------|------|------|------|
| ResearchAgent | 建仓分析 | 股票代码 + 用户偏好 | 多维度评分 + 建议 |
| StrategyAgent | 策略建议 | 持仓信息 | 操作建议 + 理由 |
| SectorAgent | 板块分析 | 市场类型 | 板块排行 + 推荐 |
| PortfolioAgent | 组合优化 | 持仓组合 | 风险评估 + 优化方案 |

#### 提示词管理

**设计原则**：
- 模板化管理，支持版本控制
- 使用配置中心动态切换
- 包含用户偏好、市场数据、输出格式约束

**容错机制**：
- Token 超限 → 截断历史数据
- LLM 调用失败 → 3次重试 + 熔断
- 降级方案 → 基于规则的评分引擎

#### LLM 客户端设计

**功能特性**：
- 多模型支持（DeepSeek/OpenAI/Claude）
- 智能路由（根据任务类型选择模型）
- 成本控制（Token 预估 + 限额）
- 限流保护（每分钟请求数限制）
- 熔断降级（连续失败 N 次后熔断）

### 3.2 市场数据适配器

#### 架构设计

```
MarketDataService
  ↓
DataAggregator (数据聚合)
  ↓
┌─────────────┬─────────────┐
↓             ↓             ↓
AkshareAdapter YfinanceAdapter FallbackAdapter
(A股数据)      (美港股数据)    (降级数据)
  ↓             ↓             ↓
Python 服务    Python 服务    缓存/默认值
(HTTP/gRPC)    (HTTP/gRPC)
```

#### 设计要点

**1. 适配器接口**
```java
public interface MarketDataAdapter {
    QuoteData getQuote(String symbol);
    List<KLineData> getKLine(String symbol, String period, int limit);
    FundamentalData getFundamental(String symbol);
    // ... 其他接口
}
```

**2. Python 服务集成**
- akshare 和 yfinance 是 Python 库，需独立部署
- 通过 HTTP/gRPC 提供数据服务
- 使用 Docker 容器化部署

**3. 容错机制**
- 限流：每个数据源独立限流（RateLimiter）
- 重试：失败后自动重试 3 次（Resilience4j）
- 熔断：连续失败 5 次后熔断 30 秒
- 降级：从 Redis 缓存读取历史数据

**4. 数据质量校验**
- 价格范围校验（防止异常数据）
- 时间戳校验（数据新鲜度）
- 必填字段校验

### 3.3 缓存策略设计

#### 缓存分层

| 层级 | 缓存内容 | 过期时间 | 更新策略 |
|------|---------|---------|---------|
| **L1 本地缓存** | 股票基本信息 | 1小时 | 被动失效 |
| **L2 Redis** | 实时行情 | 5分钟 | 主动刷新 |
| **L3 Redis** | AI 分析结果 | 30分钟 | 懒加载 |

#### 缓存 Key 设计

```
# 命名规范：模块:业务:参数
investment:quote:{symbol}              # 实时行情
investment:quote:{symbol}:kline:{period}  # K线数据
investment:analysis:{symbol}:{type}    # AI 分析结果
investment:sector:ranking              # 板块排行
investment:user:{userId}:positions     # 用户持仓列表
```

#### 缓存防护

**1. 缓存穿透（查询不存在的数据）**
- 布隆过滤器预过滤非法股票代码
- 空结果也缓存（TTL=5分钟）

**2. 缓存击穿（热点数据过期）**
- 分布式锁保护热点数据更新
- 提前异步刷新即将过期的热点数据

**3. 缓存雪崩（大量缓存同时过期）**
- 过期时间加随机值（±10%）
- 缓存预热（启动时加载热门股票）

### 3.4 消息推送架构

#### 推送流程

```
定时任务触发 (14:45)
  ↓
生成推送内容
  ↓
分批发送到消息队列 (RabbitMQ)
  ↓
消费者并发处理 (5-10 线程)
  ↓
调用推送服务 (APP Push / 站内信)
  ↓
记录推送历史
```

#### 削峰填谷设计

**问题**：14:45 同时推送 10 万用户，瞬时压力大

**方案**：
1. **分批入队**：每批 100 个用户，分 1000 批
2. **限流消费**：消费者 QPS 限制为 100
3. **失败重试**：失败消息进入死信队列，延迟重试

#### 推送配置

| 推送类型 | 触发时间 | 推送对象 | 优先级 |
|---------|---------|---------|-------|
| 建仓推荐 | 交易日 14:45 | 开启推送用户 | 高 |
| 持仓诊断 | 交易日 15:00 | 有持仓用户 | 高 |
| 异动提醒 | 实时 | 相关用户 | 紧急 |
| 板块周报 | 周一 09:00 | 所有用户 | 中 |

## 六、技术风险与应对

### 6.1 外部 API 限流

**风险**：akshare/yfinance 限流导致数据获取失败

**应对**：
1. 多级缓存（本地 + Redis）
2. 限流控制（每分钟最多 60 次）
3. 降级方案（从缓存读取历史数据）
4. 备用数据源（同时接入多个数据源）

### 6.2 LLM 调用失败

**风险**：LLM 服务不可用或响应超时

**应对**：
1. 重试机制（3 次指数退避）
2. 熔断保护（连续失败 5 次熔断 30 秒）
3. 降级方案（基于规则的评分引擎）
4. 多模型切换（主用 DeepSeek，备用 OpenAI）

### 6.3 数据一致性

**风险**：并发操作导致持仓数据不一致

**应对**：
1. 乐观锁（version 字段）
2. 分布式锁（Redis）
3. 定时数据校验任务
4. 手动修正工具

### 6.4 消息推送延迟

**风险**：14:45 大量推送导致延迟

**应对**：
1. 消息队列削峰（分批入队）
2. 限流消费（控制 QPS）
3. 异步处理（推送不阻塞主流程）
4. 优先级队列（紧急消息优先）
